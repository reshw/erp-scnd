## 대시보드 차대 불균형 체크 — PostgREST가 .limit(100000)을 조용히 1000행으로 잘라내던 버그

**결정일:** 2026-08-06
**계기:** 대시보드에 실제로는 균형 잡힌 전표 3건(#340/#413/#415)이 "차대 불균형"으로,
NADIA 프로젝트가 +410,454 불균형으로 잘못 표시됨. 이 세션에서 새 전표를 여러 건
발행하면서 `journal_lines` 총 행 수가 처음으로 1000을 넘겨서(1033행) 드러났다.

- **원인**: `src/app/(erp)/page.tsx`의 무결성 체크가 `.from('journal_lines').select(...).limit(100000)`으로
  전체 행을 가져오려 했는데, Supabase PostgREST는 서버 설정(`db-max-rows`, 기본 1000)을
  넘는 `.limit()` 요청을 조용히 1000행으로 잘라낸다(에러 없음). 실제로 1000행만 오는지
  직접 확인해서 재현함. 그 결과 뒤쪽 33행이 통째로 빠져서, 그 33행이 걸린 전표들의
  차변/대변 합계가 실제보다 적게 잡혀 가짜 불균형으로 보였다(개별 전표는 물론, 그
  전표들이 속한 NADIA 프로젝트 전체 합계도 같이 틀어짐).
- **수정**: `.range()`로 직접 페이지네이션하는 `fetchAllRows()` 헬퍼를 추가해서 1000행
  단위로 끝까지 반복 조회하도록 변경. `journals` 테이블 쪽(같은 패턴, `.limit(10000)`)도
  아직 10,000행이 안 됐지만 같은 문제가 재발할 걸 알기에 선제적으로 같이 고침.
- **검증**: 페이지네이션 적용 후 `journal_lines` 1033행 전부 수신 확인, 불균형 전표
  0건으로 정상화됨.
- **교훈**: Supabase/PostgREST `.limit(N)`은 서버 max-rows 설정보다 큰 N을 주면 예외 없이
  조용히 잘리므로, 전체 테이블을 훑어야 하는 코드는 항상 `.range()` 페이지네이션을 써야
  한다 — 이번처럼 데이터가 어느 문턱을 넘기 전까지는 버그가 안 드러나서 놓치기 쉽다.

**후속 개선(같은 날) — 페이지네이션도 결국 매 렌더마다 전체 테이블을 읽는 건 마찬가지라는
지적으로, DB 뷰로 재작업.** `unbalanced_journals`/`unbalanced_project_totals`(027
마이그레이션)를 신설해 `SUM/GROUP BY/HAVING`을 Postgres가 인덱스
(`idx_journal_lines_journal_id`, `idx_journals_project_id`) 타고 직접 계산하게 하고,
애플리케이션은 그 결과(정상 상태면 0건)만 받아오도록 변경. `.range()` 페이지네이션
헬퍼는 통째로 제거 — 행이 아무리 늘어나도 응답 크기가 안 늘어나므로 이 문제가
근본적으로 재발하지 않는다.

## /staff 대시보드 — 매출 카드 부가세 제외로 되돌림 + 가용잔액 카드 신설

**결정일:** 2026-08-06
**계기:** 매출은 부가세 포함, 비용은 발생주의·부가세 제외로 기준이 달라서 매출-비용
차액이 실질 손익이 안 되는 문제를 사장님이 지적(개발자 전달용 요청서로 전달됨).
매출 카드를 부가세 포함으로 바꾼 지 얼마 안 됐는데 다시 되돌림 — 두 표시 모두
나름의 이유가 있었지만("실입금액과 맞춰보기" vs "손익 비교 가능") 후자가 우선순위로
확정.

- 매출 카드: `{month} 매출 (부가세 포함)` + `(순매출/부가세)` 병기 → `{month} 순매출`
  단독 표시로 되돌림. VAT 계산 코드(`revenueAccounts`/`vat`/`revenueGross` 등)도
  안 쓰므로 같이 제거.
- **가용잔액(운영 가능 자금)** 카드 신설: `보통예금+현금 − 부가세 순채무(부가세예수금
  −부가세대급금) − 대표자 정산대기금 − 미지급금(매입)`, 전부 기준일(asOfDate)까지
  누적. "통장 잔액만 봐서는 지금 얼마를 써도 되는지 알 수 없어서 사장님이 개인자금을
  투입하는 일이 생긴다"는 문제를 대시보드에서 바로 보여주려는 목적.
- **대표자 정산대기금 계산 — 새 계정 신설 안 하고 기존 출자금/인출금(양석환) 순액으로 계산.**
  요청서는 `가지급금(대표이사)`/`가수금(대표이사)` 신규 계정을 "추천"했지만, 바로 전
  세션에서 마통 파킹 오분류를 고치면서 이미 "대표자가 회사를 위해 대신 낸 돈"은
  `출자금(양석환, 투입)`, "회사 돈이 대표자에게 나간 것"은 `인출금(양석환, 인출)`로
  깔끔하게 분리해뒀던 참이라(장기차입금엔 더 이상 안 섞임 — 위 "직원용 ERP AI 에이전트"
  항목과 이어지는 세션 참고), 새 계정 없이 `출자금(양석환) 잔액 − 인출금(양석환) 잔액`
  (프로젝트 스코프)만으로 요청서의 "대표자 정산대기금" 수치와 동일하게 계산됨을 확인.
  **다만 이건 판단이 갈릴 수 있는 지점이다** — 출자금은 원래 "영구 자본 투입" 개념이라
  단기 정산 대기 채무 추적과 성격이 다르다는 반론도 가능하므로, 나중에 이 계산이
  헷갈리거나 출자금 잔액의 "진짜 자본 투입분"과 "정산 대기분"을 구분해야 할 필요가
  생기면 요청서대로 전용 계정 신설을 재검토할 것.
- "조만간 지급 확정된 미지급금"은 만기/확정 여부를 구분할 필드가 없어 그냥 미지급금(매입)
  전체 잔액을 씀(단순화 — 지금 이 프로젝트엔 미지급금(원리금) 잔액이 없어 실질적으로
  문제 안 됨, 필요해지면 재검토).

**추가 변경(이후 세션):**

- 매출/비용 카드는 위 결정과 달리 **다시 부가세 포함 총액 + (순액/부가세) 병기로
  되돌아감**(세션 밖에서 재변경) — `{month} 매출 (부가세 포함)`/`{month} 비용 (부가세 포함)`.
  비용 쪽도 매입 계정과 짝지어 부가세대급금을 같은 방식으로 골라내는 `relatedVat()`
  헬퍼로 일반화됨. 이 문서의 "순매출 단독 표시로 되돌림" 서술은 더 이상 코드와 안 맞으니
  참고만 할 것 — 다음에 다시 바뀌면 여기 갱신.
- **대표 개인투입금** 카드 분리 신설: 가용잔액 계산에 묻혀있던 대표자 정산대기금을
  부호를 뒤집어(`-founderSettlement`) 별도 카드로 노출. 회사 관점("얼마를 갚아야 하나",
  양수)이 아니라 대표 본인 관점("내 돈이 얼마나 물려있나", 마이너스일수록 큼)이 더
  직관적이라는 사용자 피드백 반영.
- **예정잔고** 카드 신설: `가용잔액 + 미수금(신용카드/무통장입금/PG) 합계` — "미수금이
  전부 들어오면 얼마가 되는지" 전망치. 가용잔액과 별도 카드로, 둘 다 항상 같이 노출.
- **대표 개인투입금 카드 다시 제거.** "필요없다"는 피드백으로 롤백.
- **가수금(대표이사) 계정 신설, 출자금과 분리.** 위 §"대표자 정산대기금 계산" 항목의
  우려가 실제로 맞아떨어짐 — 보크트리(822,000)/루시아나스튜디오(399,999) 대납분을
  "출자금 제외하고 추후정산 대상으로 잡아달라"는 요청으로, `가수금(대표이사)` 계정을
  새로 만들어(활동유형 `개인`, 정상측 대변, 증가 `발생`, 감소 `정산`) 그 두 건만
  재분류했다. 나머지 진짜 자본금(65,000)은 출자금에 그대로 남음. 상세 판단 기준은
  `docs/manual-posting-conventions.md`의 "가수금(대표이사)" 절 참고.
- **버그: 가수금 분리 직후 가용잔액이 과도하게 나빠짐(-1,230,908) — 인출금 넷팅 누락.**
  가수금(대표이사)만 빼고 인출금(양석환)을 formula에서 통째로 빠뜨림. NADIA 정산금이
  인출금으로 빠져나가 마통에 들어간 것(그가 NADIA에 갚아야 할 돈)과, 그가 마통에서 다시
  인출해 NADIA 청구서를 대신 갚아준 것(NADIA가 그에게 갚아야 할 돈, 가수금)은 반대
  방향인데 가수금 한쪽만 빼면 인출금 쪽 채권이 누락돼 이중으로 나쁘게 잡힌다. **대표자
  관련 순채무 = 가수금(대표이사) − 인출금(양석환)**으로 수정. 수정 후 가용잔액
  -330,289, 예정잔고 279,711(양수로 정상화) — NADIA 실데이터로 검증 완료.
- 남아있던 출자금(양석환) 65,000 중 당근마켓 광고캐시 충전분 50,000(#414, 하나카드
  대납)도 같은 이유로 가수금(대표이사)로 재분류. 진짜 자본은 #340 "일반출자" 15,000만
  남음. 재분류 후 가용잔액 -380,289, 예정잔고 229,711.
- **NADIA 프로젝트 출자금 전수조사 후 마지막 #340(15,000)도 재분류, NADIA 출자금 잔액
  0으로 정리.** #340은 앞의 세 건과 달리 마통 경유가 아니라 양석환이 회사 계좌(통장-
  기업-레저)에 현금 15,000을 직접 입금한 건이라 처음엔 순수 자본으로 보였으나, 사용자
  확인 결과 **보증보험 가입비용 재원**이었음(특정 목적 자금, 상환 불필요한 자본이
  아니었음) — 가수금(대표이사)로 재분류. 결과적으로 NADIA 프로젝트의 출자금(양석환)은
  전량 가수금(대표이사)였던 것으로 정리됨(0원). 최종: 가수금(대표이사) 1,286,999 −
  인출금(양석환) 915,164 = 대표자 관련 순채무 371,835, 가용잔액 -395,289, 예정잔고
  214,711.

## 직원용 ERP AI 에이전트 — 스코프 DB 키 + 전표 대기열 + 승인 워크플로 + 직원 웹 조회

**결정일:** 2026-08-06
**계기:** NADIA 직원(영업직, 회계 비전문)에게 회계 업무를 열어주려는데 ERP 화면이 너무
어려움. 이 세션에서 사용자가 나에게 자연어로 "전표 쳐줘"라고 하면 발행해주는 방식을
직원에게도 주자는 아이디어에서 출발.

### 폐기된 대안들 (설계를 여러 번 뒤집으며 확정)

1. **2026-07-22~23 원안(웹 로그인 + status 플래그)**: 직원이 웹 화면에서 직접 입력, 미승인
   전표는 status 컬럼으로 구분. **기각** — journals를 직접 읽는 20여 곳이 필터를 하나라도
   빠뜨리면 미승인 건이 손익/VAT에 샌다(당시 사용자가 직접 철회).
2. **웹 로그인 + RLS + 승인 UI(이번 세션 1차안)**: 직원이 웹 화면으로 입력, RLS로 프로젝트
   제한. **기각** — 웹 입력 자체를 안 쓰기로 방향이 바뀜(AI 대화형 입력 채택). RLS는
   애초에 이 앱의 데이터 접근이 거의 다 `createAdminClient()`(service_role, RLS 우회)를
   거쳐서 웹 쪽에선 실효성 없다는 것도 확인됨.
3. **NADIA 특화 별도 폴더(2차안)**: 직원 AI 키트를 "NADIA용"으로 하드코딩. **기각** —
   "다양한 프로젝트에 대응되는 범용 에이전트여야 한다"는 지적으로, 스코프/관행을 폴더가
   아니라 DB(`staff_access`, `posting_conventions`)에서 읽어오는 구조로 전환.
4. **직원용 별도 웹 없이 AI만(3차안)**: "잔액 얼마야?"를 AI에게 물어보게만 함. **기각** —
   "AI가 말하는 숫자는 신뢰가 안 간다"는 지적으로, 확정 수치는 반드시 ERP 웹(`/staff`)에서
   확인하게 함(AI는 입력 전용, 조회는 웹).

### 확정된 구조

- **입력(AI)**: 직원은 `D:\dev\erp-ai-agent\`(별도 git repo, 프로젝트 중립)를 받아 자기
  DB 키를 `.env`에 넣고 Claude Code로 대화한다. 스코프(`staff_access`)와 전표 관행
  (`posting_conventions`)은 전부 DB에서 읽어오므로 폴더 자체엔 프로젝트 지식이 없다.
- **방어선은 Postgres 권한 자체** — `journals`/`journal_lines`에 INSERT/UPDATE/DELETE
  GRANT를 아예 안 줘서, 직원 AI가 뭘 하려 하든 DB가 거부한다(RLS 이전 단계의 원천 차단).
  쓸 수 있는 건 `journal_drafts`/`journal_draft_lines`(대기열)뿐 — SAP 문서 파킹과 동일한
  원리. RLS는 SELECT 스코프(자기 프로젝트만)와 draft INSERT 시 project_id 강제에 씀.
  그룹 role `project_scoped_agent`에 정책을 걸어서 다음 직원 추가는 `GRANT ... TO`
  한 줄로 끝남.
- **승인**: 관리자가 `/journal-drafts`(웹) 또는 나에게 "대기열 확인해줘"(대화)로 승인/반려.
  승인 시 `journal_no` 채번 후 `journals`/`journal_lines`에 확정 발행.
- **조회(웹)**: 직원은 `/staff`(잔액·손익), `/staff/journals`(전표 조회),
  `/staff/drafts`(내 상신함)만 볼 수 있다. `src/proxy.ts`가 화이트리스트 밖 전부를
  `/staff`로 리다이렉트(**주의**: `startsWith('/staff')`로 짰다가 `/staff-access`
  까지 통과해버리는 버그가 실제로 발생해 `=== '/staff' || startsWith('/staff/')`로
  수정 — 접두어 매칭 화이트리스트를 짤 때 반복될 수 있는 실수라 기록해둠).
- **관리**: `/staff-access`(관리자 전용)에서 발급(AI 키+웹 로그인 동시 생성)/차단

## /clearings — "기간" 필터를 "기준일" 스냅샷 + 프로젝트 복수선택으로 재설계

**결정일:** 2026-08-09
**계기:** 루시아나스튜디오 건(발생 #412 7/29, 반제 #413 8/4)에서 월별 기간 필터로 보면
반제가 다음 달로 잘려나가 미결로 잘못 보이는 문제 실제 발견. "월 2개씩 보여주기"도 제안했으나
3개월 이상 걸치는 케이스(대출 이자 등)엔 여전히 깨지는 반창고라 기각.

- **근본 원인**: 미결잔액은 회계적으로 "기간(period)" 개념이 아니라 "기준일(as-of) 스냅샷"
  개념인데, 기존 UI가 from~to 활동 필터 하나로 잔액까지 계산해서 발생·반제가 필터 경계를
  걸치면 항상 이런 착시가 생김
- **바뀐 것**: `from`(시작일) 제거, `to`를 **기준일(as_of)**로 재정의 — 미결잔액은 항상
  "기준일까지 전체 누적"으로 계산(시작 하한 없음). 이러면 발생·반제가 몇 달을 걸치든 기준일만
  그 이후면 항상 정확
- 프로젝트 필터를 단일 SearchSelect → **체크리스트 복수선택**으로 변경(`project_ids`,
  comma-separated) — "전체 누적"이 너무 광범위하다는 지적에 따라 시간 축(기준일)과 별개로
  차원 축(프로젝트)은 계속 좁혀서 볼 수 있게 유지
- `params.project_id`/`from` 단일값을 참조하던 `ledgerUrl()`도 `project_ids`(1개 선택시만
  전달)/`as_of`로 갱신
- DateRangePicker 컴포넌트는 그대로 둠(ledger/journals에서 계속 사용 — 그 페이지들은
  "이 기간에 무슨 일이 있었나" 활동 조회가 목적이라 기간 필터가 맞는 모델. /clearings만
  성격이 달라 별도 UI로 분리)

## 대출 자동선발행 — "이미 전표 있으면 스킵" 매칭 로직 폐기 → 미지급금(기타) 선발행 + 반제

**결정일:** 2026-07-27

적용하기로 함.

### 대상 범위

**마이너스통장(마통) 제외한 모든 대출** (원리금균등: 국민은행/IM뱅크/농협은행 주택담보대출,
TR.F(양) / 만기일시: TR.B 시리즈 등). 처음엔 "원리금균등만"으로 좁혀 물었으나, 이 질문
자체가 범위를 잘못 좁힌 것이었음 — 사용자 의도는 "마통만 빼고 전부"였음(만기일시도
포함). 마통은 `spending_executions`을 아예 거치지 않는 별도 체계(정액/잔여 배분, 위 결정
참조)라 원래도 이번 변경과 무관.

크론 여부는 중간에 방향이 두 번 바뀌었음: 처음엔 GitHub Actions 완전자동화 → "크론 필요
없다, 수동 집행 유지"로 축소 → 다시 "만드세요"로 돌아와 최종적으로 **크론 자동화로 확정**.

  `pending`/고아 `executed`(journal_id 없음) 상태로 갖고 있음 발견. **기존 전표는 건드리지
  않기로 결정**(그 시점엔 미지급이 아니라 실제 지출을 기록한 것이므로) — "정확히 오늘만"
  제한 덕에 크론이 이 과거분을 애초에 볼 일이 없어 별도 정리 없이도 안전함을 확인.
- **7월분 재구성 및 중복 발견**: 위 9건 실집행 중 7건(IM뱅크·TR.B(이)_2026_20M 제외)이
  이미 07-06에 완결돼있던 실제 단일전표(원금+이자/보통예금 직결)와 **중복**이었음(같은
  대출-월에 spending_executions 행이 여러 개 쌓여있던 기존 데이터 문제 — 고아 pending과
  이미 실제 전표에 연결된 executed 행이 공존). 처음엔 제 중복만 지우고 기존 단일전표에
  재연결했으나, 사용자가 "8월부터 갈 새 모델대로 7월도 부채인식+반제 두 전표로 재구성해
  달라"고 정정 — 기존 단일전표를 삭제하고 `insertJournalWithLines`로 (1)
  원금+이자/미지급금(기타), (2) 미지급금(기타)/보통예금(반제) 두 전표씩 재발행,
  `journals.related_journals`로 서로 교차 연결. 6월 이전 이력은 손대지 않음(사용자 결정,
  세션 종료 후 별도로 전체 점검 예정).
- **PL_EXCLUDE_SUBTYPES 누락 발견**: 반제 전표의 미지급금 차변 라인이
  `insertJournalWithLines`(`lineClassification`) 경로를 타면 `activity_subtype`이 라벨
  (`비용집행`)이 아니라 타입(`반제처리`)으로 찍히는데, `/monthly` 손익추이의
  `PL_EXCLUDE_SUBTYPES`엔 `반제처리`가 빠져있어 반제 전표가 비용으로 중복 집계될 뻔함.
  DB 전체에서 이 subtype을 쓰는 행이 방금 만든 7건뿐이라 과거 데이터 오염은 없었음(같은
  경로를 쓰는 `/clearings/settle`의 실사용 사례가 아직 없었다는 뜻이기도 함) — 즉시
  `PL_EXCLUDE_SUBTYPES`에 `반제처리` 추가로 수정.
- **과거 이력 전체 재연결(2026-07-27, "6월 이전은 두자" 이후 재요청)**: 6개 대출(마통

  IM뱅크만의 문제가 아니라 전 대출 공통으로 `spending_executions` 연결만 누락된 것으로
  확인됨(계정 자체는 이미 정확 — 실제 미지급이 발생한 적은 없음). 거래처+월+**금액**

## /receivables — 정산 대사 전용 화면 신설

**결정일:** 2026-07-27
**계기:** 미수금(신용카드) 발생액이 이상해 보인다는 지적을 따라가다 보니, `/clearings`는
거래처별 그룹핑 화면인데 tt 결제 고객은 애초에 ERP 거래처가 아니라 `counterparty_id/name`이
전부 null이라 전부 "(거래처 없음)" 한 줄로 뭉쳐 쓸모가 없었음. 게다가 "취소"(반대분개)가
"반제"(실제 수금)와 같은 집계 버킷에 섞여 숫자가 실제 거래량과 안 맞아 보임(잔액 자체는
정확). "회계적인 화면 말고, 찍힌 것 vs 실제 입금만, 취소는 아예 안 보이게" 요청으로
`/clearings`와 별개로 새 화면을 만듦.

### 무엇을 만들었나

- `timetable_payment_postings.settlement_journal_id`(021 마이그레이션) — 어느 승인 posting이
  어느 정산 전표로 정리됐는지 직접 연결. 텍스트로 "전표 #331" 식으로 적어두던 기존 수동
  방식은 조회가 안 돼서 구조화된 컬럼으로 대체.
- `POST /api/timetable/payments/settle` — posting 하나(external_id) + 실입금액 + 날짜를
  받아 `차변 보통예금(입금액) + 차변 판관비(지급수수료)(차액, 0이면 생략) / 대변 [원래
  잡힌 계정]`으로 정산 전표를 내고 `settlement_journal_id`를 채움.
- `/receivables` 페이지 — 계정별(미수금 신용카드/무통장입금/PG, 현금)로 미정산 건만 나열.
  **취소된 원거래는 `reverses_external_id`로 걸러서 화면에 아예 안 보이게** 함(요청사항).
  정산완료 건은 접힌 상세(`<details>`)로 하단에 남김.
- `receivableAccountName()`을 `sync/route.ts`에서 `src/lib/timetablePayments.ts`로 빼서
  sync 라우트와 이 화면이 채널→계정 매핑을 공유(로직 두 곳에 따로 안 둠).

### 실데이터로 검증하다 발견한 것 — tt가 external_id를 사후에 바꿈

과거에 수동으로 반제 처리했던 두 건(전표 #339, #347)에 `settlement_journal_id`를 처음엔
당시 알고 있던 external_id(예: `732731081715325399`)로 연결했는데, 확인해보니 **tt가
7/23에 이 결제들을 "재배분(reallocation)" 처리하면서 원래 id는 취소하고 같은 금액으로
새 suffix가 붙은 id(`732731081715325399:fe48dad1-...`)를 새로 발행**해뒀었음. 계좌 잔액
자체는 우연히 맞아떨어졌지만(취소분+원 settlement가 서로 상쇄), 건별 추적 목적에서는
이미 취소된 옛날 id에 링크가 붙어있고 정작 지금 유효한 id는 미정산으로 잘못 보이는
상태였음 — `settlement_journal_id`를 현재 유효한 suffix-id 쪽으로 옮겨서 수정.

**tt의 external_id가 매칭/재배분 시점에 바뀔 수 있다는 게 재확인됨** — 대관료 API 스레드와
이번 현금 채널 백필 때도 같은 패턴이 나왔음(누적 3회째). 앞으로 이 계열 작업 때마다
"현재 tt 라이브 API 기준으로 유효한 id인지" 재확인하는 걸 기본 절차로 삼는다.

## timetable 현금(toss/CASH) 채널 자동전표 제외 → 포함으로 전환

**결정일:** 2026-07-27
**계기:** `/clearings`에서 미수금(신용카드) 발생액이 이상해 보인다는 지적 → 실제 원인은
현금(50만원) 결제가 애초에 스킵돼서 안 들어온 것 + 취소/반제 혼동 + 거래처 없음 3가지가
겹친 것으로 확인. 그중 "현금 채널 자동전표 제외"는 재검토해서 뒤집음.

### 왜 원래 제외했었나 / 왜 뒤집었나

7/22 결정 당시엔 "현금 수령 — 금고/입금 흐름을 사람이 판단해야 함"이라고 봐서
`toss/CASH`·`cash`를 스킵 대상에 넣었음. 그런데 실제로는 카드/PG처럼 **정산 지연 자체가
없음** — 매장에서 즉시 현금으로 받는 거라 미수금 단계가 필요 없고, "판매 인식"과 "통장
입금"을 분리하면 사람 판단이 필요한 부분(언제 은행에 넣었는지)만 남기고 판매 인식은
카드/PG와 똑같이 바로 자동화할 수 있음.

### 무엇을 바꿨나

- **`현금` 계정과목 신설** (`020_cash_on_hand_account.sql`, `보통예금`과 같은 activity_type
  `현금`이라 손익 집계에서 자동 제외됨 — 7/22 B/S 오집계 버그와 같은 함정 없음).
- `src/app/api/timetable/payments/sync/route.ts`의 `receivableAccountName()`:
  `toss/CASH`·`source='cash'` → `null`(스킵) 대신 **`현금`** 반환. 승인 시점에
  `차변 현금 / 대변 판매수입+부가세예수금`으로 바로 발행(미수금 채널과 같은 패턴, 계정만
  다름). 통장 입금(현금 시재 → 보통예금 이체)은 여전히 별도 수기 전표.
- `toss/EXTERNAL`은 그대로 제외 유지 — 이건 "사람 판단 대기"가 아니라 **어느 채널로도
  정산 경로를 모르는** 별개 문제라 같이 뒤집지 않음.

### 백필

이미 스킵돼 있던 `timetable_payment_postings` 중 실제 반영이 필요한 건 1개뿐이었음
(전표 #346, 2026-07-14, 500,000원 개인레슨 10회권). 처리 과정에서 발견한 것:

- **같은 결제가 external_id 두 개로 남아있었음** — `732233653970973243`(초기 미매칭 원행)과
  `732233653970973243:b32d2d28-...`(매칭 후 tt가 다시 부여한 id). tt 라이브 API를 직접
  조회해 현재는 후자만 유효함을 확인 후 그것만 백필, 전자는 그대로 방치(중복 발행 방지).
  **tt의 external_id가 매칭 전후로 바뀔 수 있다는 뜻** — pg-schema 스레드에서 이미 우려했던
  "provider_txid가 채널별로 안정적이어야 멱등이 깨지지 않는다"는 지점이 실제로 발생한 사례.
  재발하면 같은 방식(tt 라이브 API로 현재 유효 id 확인 후 그것만 처리)으로 대응.
- `cash/cash` 30,000원 건(발생+같은 날 취소, 순액 0)은 백필 안 함 — 어차피 순액 0이라 굳이

## timetable 결제원장 커서 동기화 (매출전표 자동발행)

**결정일:** 2026-07-22
**구현 범위:** `POST /api/timetable/payments/sync` + 일 1회 GitHub Actions 배치

timetable이 append-only 연동원장(`payments`)과 읽기전용 API를 완성해 착수 조건이 충족됨.

**전표 형태** — 승인건: 차변 `미수금(채널)` 총액 / 대변 `판매수입` 공급가 + `부가세예수금` 세액.

1. **append는 연동 원장에만 적용해도 회계 요건 충족.** 단 취소/환불은 원본 행 in-place update가 아니라 **반대 이벤트 행을 append** 해야 함 (ERP가 발행한 전표와 취소전표 대사를 위해). timetable 앱 내부 테이블(잔여횟수·상태 로직)은 안 건드려도 됨.
2. **부분 배분 수용 — 배분(allocation) 단위 행으로 수신.** 결제 1건이 N개 매출로 쪼개지면 N행. 단 같은 원결제임을 알 그룹키(`payment_group_id`/`provider_txid`)를 각 행에 실어달라 (배분합 검증 + 정산 매칭용).
3. **인증=고정 Bearer(venue-fee와 동일), 페이지네이션=`updated_at` 커서(`?since=&limit=`, 응답 `next_cursor`), 시각=UTC ISO8601.** KST 변환은 ERP 담당.
4. **테스트 데이터는 `is_test` 플래그만, 조회 측(ERP)에서 `is_test=false` 필터.**
5. **프로젝트 귀속 = `일반-LEISURE` 단일** (나디아요가 한 곳뿐, 연동 원장에 귀속 필드 불필요).

**ERP 착수 조건:** timetable이 (1)실시간 반영 (2)append 취소 (3)읽기전용 API 셋을 완료하면 그때 ERP가 커서 동기화 코드 작성. 그 전엔 착수 안 함. 정산(입금) 데이터는 후속 단계.

### 챗 어시스턴트 이식 — 거절

timetable이 관리자 챗 어시스턴트(Anthropic 기반) 이식을 제안했으나 **도입하지 않기로 함** (`inbox/timetable/from-erp__260722-assist-chat.md`).

`clearings` 테이블을 추가해서 발생 라인과 반제 라인을 1:1로 연결하는 기능.

#### 왜 보류했나

**자동매칭이 현실적으로 어렵다:**
- 발생일과 반제일이 다른 게 기본 (당연히 날짜 매칭 불가)
- 부분 지급 / 합산 지급 / 같은 금액 반복 발생 등 예외가 많음
- FIFO 자동제안 수준은 가능하지만 오매칭 위험
- 적요 텍스트 AI 분석은 적요를 꼼꼼히 쓰지 않으면 useless

**과했던 것:**
- `clearings` 테이블 마이그레이션
- 라인별 "미결/부분반제/완결" 상태 UI
- 자동매칭 + 수동매칭 모달

#### 거래처별 잔액만으로 충분한 이유

미지급금 분석의 실질적 목적은 "거래처 A에 얼마 남아있나"이지,  
"#123 인보이스가 #167 지급건으로 상쇄됐는가"가 아닌 경우가 대부분.  
잔액이 0이면 반제 완결, 잔액이 남으면 미결 — 이 정도로 실무 파악 가능.

#### 나중에 필요하면

거래처별 잔액에서 특정 거래처의 잔액이 왜 남았는지 원장 드릴다운으로 확인 가능.  
실제로 라인 매칭이 필요해지면 그때 `clearings` 테이블 추가.

## 국세청 매입 세금계산서 자동 접수(전표 자동발행) — 검토 후 보류

**결정일:** 2026-08-04
**성격:** 외부 작업 지시서 검토 후 방향 결정 (구현 안 함)

### 배경

작업 지시서는 SendGrid/SES/Mailgun 인바운드 웹훅 + busboy/formidable로 국세청 tax.html 첨부를 받아 복호화·파싱·전표 자동발행하는 파이프라인을 요청했음. 그러나 실제 메일 수신 경로는 Cloudflare Email Routing → `mailer-worker`(Firestore 저장 + R2 첨부 업로드)이며 SendGrid 계열이 아니어서, 지시서의 아키텍처 전제부터 실제와 달랐음.

### 검토한 경로들 (전부 보류)

1. **국세청(hometax.go.kr) 자체 보안메일 파싱** — 실 샘플(`NTS_eTaxInvoice (8).html`, 사업자번호 1741202919)로 국세청 크립토 JS(`cri_ems_nt.js`/`seed.js`/`aes.js`/`md5.js`, srtk.hometax.go.kr에서 원본 다운로드해 분석)를 완전히 리버스함:
   - `idCriHeader`(base64 → 바이트별 XOR `0x6B`)를 풀면 `ContentEncryptionAlgorithm`(1=AES/2=SEED/3=ARIA)·`HashKey`·첨부 메타가 평문 라인(`key:value`, 구분자 `\r\n`/`\n`)으로 들어있음
   - 키 = `MD5(사업자등록번호)`, IV = 0 고정(16바이트). `HashKey`를 그 키로 복호화한 UTF-8 문자열이 키의 hex 표현과 일치하면 비밀번호 통과
   - 통과하면 `idCriPcContents`/`idCriMobileContents`(및 `idCriAttachContentsN`)를 같은 키·IV로 복호화 → 평문 세금계산서 HTML/첨부
   - 알고리즘 자체는 재현 가능함을 확인했으나, **이 알림메일은 발행처가 홈택스에서 직접 발행한 경우에만 옴.** 실제로는 거래처 대부분(당근마켓 등)이 팝빌 같은 발행대행사를 쓰고, 그 경우 팝빌이 자체 이메일로 알림을 보내며 국세청발 메일 자체가 안 옴(NHN은 또 자체 시스템) → 커버리지가 낮아 구현 가치 낮음
2. **팝빌/바로빌 등 유료 발행대행 API 가입 후 폴링(크론)** — 비즈플레이 등 대기업 결재시스템이 쓰는 표준 패턴(인가 ASP에 인증서 위임 + 주기적 조회)이지만, 신규 유료 가입을 원하지 않아 제외
3. **홈택스 자체 로그인 자동화(공동/금융인증서 또는 아이디·비번)** — 기술적으로는 스크립트 작성이 가능하나(로그인 화면의 키보드보안 프로그램은 체크박스 옵션이라 강제 아님) 정책상 보류: 인증서·계정 비밀번호를 서버에 상시 저장해 무인 로그인시키는 구조는 유출 시 세금계산서 조회 수준을 넘어 전자서명·세무신고 전체가 노출되는 리스크이고, 홈택스 이용약관상 매크로/자동접속 금지 조항과도 충돌 가능성이 높음 — 자동 로그인 자체를 구현하지 않기로 함
4. **발행사별(팝빌/NHN 등) 알림 이메일 파싱** — 발행처마다 포맷이 달라 파서를 계속 늘려야 하는 미봉책으로 판단, 채택 안 함

### 최종 결정

자동 접수 파이프라인은 만들지 않음. 매입 세금계산서가 도착하면 지금처럼 자연어로 알려주면 `ledger-entry` 방식(계정 선택은 `docs/manual-posting-conventions.md` 우선 확인)으로 전표를 대리 발행하는 기존 흐름을 유지. 증빙 문서 자체도 보관 의무가 없는 상황이라(사용자 확인), 자동 다운로드/보관 인프라의 필요성도 낮음.

**보류로 남겨둔 것(향후 값어치 생기면):** 국세청 CRI 복호화 로직은 이번에 완전히 리버스했으므로, 홈택스 직접발행 비중이 늘거나 이 알림메일이 주경로가 되는 상황이 오면 `lib/ntsDecryptor.ts` 구현은 바로 재개 가능(알고리즘은 이미 검증됨 — seed/aes/md5 JS 라이브러리를 Node `vm`으로 그대로 실행하거나 포팅).

### 무엇을 안 만들었나 / 왜

- **증빙종류(세금계산서/카드/현금영수증 구분) 컬럼:** DB에 해당 데이터가 없음. 대신 계정과목 컬럼으로 대체. 필요해지면 `journal_lines`에 증빙 유형 컬럼 추가 후 반영
- **홈택스 신고서식(정확한 갑지 양식) 재현:** 내부 증빙·세무사 전달용 요약표로 충분하다고 판단

## `/staff` 매출 상세(가계부) — timetable 결제 재매칭 워시(wash) 쌍 필터링

**결정일:** 2026-08-06
**성격:** 직원용 신규 화면(`/staff/ledger`) 구현 중 발견한 데이터 노이즈 처리

### 배경

직원용 매출 상세 리스트에서 같은 날짜·같은 금액의 "결제"/"[취소] 결제"/"정기 OO(상품명)" 3개 전표가
한 세트로 반복 등장해 실제 판매 건수보다 부풀어 보임(예: 2026-07-31 토스 29만원 건 = #407 결제 +
#410 취소 + #409 "정기 주2회2개월(16회)" 세 전표). 순매출·부가세 합계는 이미 정확히 상쇄되고 있어
회계 버그는 아니고 표시(UX) 문제였음.

### 원인 확인 — timetable 쪽 "분할배분(payment_group_id)" 설계, ERP가 활용을 안 하고 있었을 뿐

`_shared/inbox/_archive/erp/from-timetable__260722-pg-schema-r2.md`(1번 항목)에 이미 답이 있었음:
timetable `payments` 원장은 토스 결제 1건이 수강권 N개로 매칭되면 배분 단위 N행을 append하고,
매칭 전 미매칭 1행에는 반대행(취소)을 붙이는 append-only 설계. `reverses_external_id`(반대행 →
원행 참조)와 `payment_group_id`(같은 원거래 배분행 공유)가 API 응답에 이미 내려오고 있었고,
ERP `timetable_payment_postings.payload`에도 이미 저장되고 있었으나 `/staff/ledger` 표시 로직이
이걸 안 쓰고 있었음. 실제 raw 데이터로 검증: 2026-07 NADIA 프로젝트 취소 13건 전부 `reverses_external_id`로
원행을 정확히 찾을 수 있었고(원인 없는 단독 취소 = 진짜 환불 0건), 지금까지는 전부 1:1 재매칭만
있었음(N>1 분할배분 실사례는 아직 없음 — timetable 쪽도 2026-07-22 시점 시뮬레이션으로만 검증했다고
확인).

### 적용한 수정

[`src/app/(staff)/staff/ledger/page.tsx`](../src/app/(staff)/staff/ledger/page.tsx) — 전표를
journal 단위로 묶은 뒤, `timetable_payment_postings.payload.reverses_external_id`로 취소↔원행
쌍을 찾아 **그 쌍만** 리스트에서 제외(합계는 원래도 0 기여라 안 바뀜). 배분행(실제 매출로 잡힌
"정기 OO" 등)은 몇 개든 그대로 개별 표시되므로, 나중에 N>1 분할배분 실사례가 생겨도 코드 변경 없이
올바르게 동작함.

### 참고

- timetable 쪽에 확인 문의를 새로 보냈음 — 실제 N>1 분할배분 사례가 아직 있는지,
  있으면 알려달라고 요청(`_shared/inbox/timetable/from-erp__260806-payment-rematch-filter.md`).
- 세무검증(8)·수수료계산서(14)·정산시각(17)은 2026-07-22 시점 여전히 미확정이었음 — 이번 문의에서
  같이 진행상황 확인.
- **"증빙 SQL" 시트 (처음엔 만들었다가 제거):** 추출 로직과 동등한 Raw SQL을 3번째 시트에 텍스트로 넣었었음. 하지만 국세청·세무대리인은 회사 내부 DB에 접근권이 없어 SQL을 실행할 방법이 없고, 그들이 요구하는 건 세금계산서 등 증빙 문서지 쿼리문이 아님 — "세무대리인/국세청 소명용"이라는 문구 자체가 과장이었다고 판단해 삭제. SQL이 필요해지면(내부 감사 추적용) 코드 주석이나 별도 문서로 남기는 게 맞음
